# Design

## Context

Мотивация и границы описаны в [proposal.md](proposal.md). Команда зарегистрирована напрямую в
`cmd/main.go:430`. В `internal/handlers/settings/settings.go` после проверки наличия чата и
отправителя и отказа в личке сразу разбираются аргументы. Тестов у этого пакета нет.

Подключён telebot v3.2.1: доступны `Context.Bot()`, `Bot.ChatMemberOf`, `ChatMember.Role`,
роли `Creator` / `Administrator` и поле `Message.SenderChat`. Метод `ChatMemberOf` уже используется
в теггере; новый клиент Telegram не требуется.

Это полный режим из-за нового контракта проверки доступа через Telegram. Здесь фиксируются
пограничные случаи авторизации и смена вероятности реакции на фото по умолчанию.

Сейчас `Config.PhotoReactChance` получает `0.75` из тега `default` в
`internal/config/config.go`. `cmd/main.go` передаёт это значение в `chatsettings.Defaults`;
провайдер подставляет его при отсутствии переопределения чата и после сброса.

## Goals / Non-Goals

**Goals:** одна проверка перед всеми ветвями команды; актуальные права именно текущего чата;
отсутствие обращений к провайдеру настроек при отказе; дефолт `photo_chance = 1` с сохранением
приоритетов настроек; проверка через реальные типы telebot без обращения к живому Telegram
в автотестах.

**Non-Goals:** общий слой авторизации для других команд, кеш ролей, хранение администраторов,
новые env-параметры и изменение `specctl`.

## Decisions

### Проверка внутри обработчика команды

Проверять доступ в начале `Handler.Handle`, до разбора аргументов и любого вызова
`settingsProvider`. Сначала проверить наличие сообщения и чата; сохранить существующий отказ
в личке, затем разрешать работу только в группах и супергруппах. Для других типов чата вернуть
отказ о доступности команды только в группе. При отсутствии сообщения/чата безопасно завершить
обработку. При отсутствии обычного отправителя и `SenderChat` также завершить её без действий.

Middleware при регистрации отклонён: ради одной команды он разносит проверку и обработку
по разным местам, а прямой вызов обработчика остаётся без защиты. Конструктор и регистрацию
команды менять не требуется.

### Обычный отправитель: точечный запрос роли

Если сообщение отправлено от пользователя, вызвать `ctx.Bot().ChatMemberOf` для текущего чата
и текущего отправителя. Разрешить только `telebot.Creator` и `telebot.Administrator`, без
проверки дополнительных флагов вроде права удалять сообщения.

Для `Member`, `Restricted`, `Left`, `Kicked` ответить: «Настройки чата доступны только
администраторам.». При ошибке запроса, пустом результате или неизвестной роли ответить:
«Не удалось проверить права. Попробуй ещё раз позже.». В обоих случаях провайдер настроек
не вызывается, подсказка и значения не отправляются. Ошибку запроса вернуть с контекстом
в существующий обработчик ошибок telebot после попытки отправить ответ; ошибку отправки
также не терять. В пользовательский ответ технические подробности не включать.

Роль проверяется при каждом вызове. Список всех администраторов и кеш разрешений отклонены:
точечного запроса достаточно, кеш сохранял бы доступ после снятия прав. Новые повторные
попытки и отдельный HTTP-клиент не добавляются; используются существующие настройки telebot.

### Сообщения от имени чата: проверка происхождения

`SenderChat` обрабатывать раньше обычного `Sender`: Telegram может подставлять в `from`
фиктивного пользователя. Если текущий чат — супергруппа и `SenderChat.ID` совпадает с её ID,
считать это командой анонимного администратора и выполнять без запроса роли фиктивного
пользователя. Для любого другого `SenderChat` отказать: «Вызови команду как администратор
от своего аккаунта или от имени этой группы.».

Это решение автора плана для полного охвата администраторов: подтверждённое Telegram
происхождение от самой супергруппы достаточно. Требовать отключить анонимность отклонено,
поскольку такая команда уже отправлена администратором. Доверять имени, подписи или роли
фиктивного отправителя нельзя.
Основание: [поле sender_chat в Telegram Bot API](https://core.telegram.org/bots/api#message).

### Новый дефолт реакции на фото

Задать в `internal/config/config.go` именованную константу `defaultPhotoReactChance` со
значением `1`. Инициализировать ею поле конфигурации до `envconfig.Process` и убрать с этого
поля прежний тег `default:"0.75"`. Envconfig сохраняет заранее установленное значение при
отсутствии переменной без default-тега и заменяет его при явно заданной переменной.
Остальные дефолты не рефакторить. Существующий `PHOTO_REACTIONS_CHANCE` сохранить;
новые env-переменные не нужны.

Приоритеты остаются прежними: сохранённый `photo_chance` чата → явно заданный
`PHOTO_REACTIONS_CHANCE` → встроенный дефолт `1`. Значение `0` является явным переопределением.
Не записывать `1` в базу для всех чатов и не заменять сохранённое `0.75`: это перезаписало бы
настройки администратора. Сброс удаляет переопределение и возвращает действующее глобальное
значение, равное `1` только при отсутствии env-переопределения.

Отображение `/settings` и сборка `Defaults` уже используют значение конфигурации. Отдельный
дефолт в обработчике фото или миграция не требуются. С вероятностью `1` случайный фильтр
пропускает каждое подходящее фото; проверки пригодности, дедупликация альбомов и обработка
ошибок остаются прежними. Контракт `photo-reactions` о применении заданной вероятности
не меняется, поэтому отдельная дельта этой capability не нужна.

### Проверки

Новый `settings_test.go`: настоящий telebot, созданный с `Offline: true`, адресом локального
`httptest.Server` и контекстом из `Bot.NewContext`. Сервер обрабатывает `getChatMember` и
`sendMessage`; проверяет переданные chat/user ID и фиксирует ответы. Провайдер настроек
заменяется тестовым двойником со счётчиками вызовов. Проверять содержимое ответа и вызовы
провайдера, а не только возвращённую ошибку.

Матрица автотестов:

- `Creator` и `Administrator` × группа/супергруппа × просмотр, изменение, сброс и подсказка;
  существующая валидация доступна только после допуска (`SET-005`–`SET-009`, `SET-013`).
- Остальные известные роли × все варианты команды, включая ошибочные аргументы и форму
  `/settings@bot_username`: отказ, ни одного обращения к провайдеру (`SET-014`).
- Ошибка Telegram, сетевая ошибка, неразбираемый ответ, пустой результат и неизвестная роль:
  отказ без обращения к провайдеру (`SET-015`); ошибка отправки отказа также возвращается.
- Два последовательных вызова с понижением роли и вызовы в разных чатах: каждый раз новый
  запрос с правильными ID (`SET-016`).
- Собственный и сторонний `SenderChat`, в том числе с отсутствующим или фиктивным `Sender`:
  собственный допускается, сторонний отказывает без запроса роли (`SET-017`, `SET-018`).
- Личка: прежний отказ без проверки роли и провайдера (`SET-010`); отсутствующие сообщение,
  чат или идентифицируемый отправитель, а также канал: безопасное завершение без провайдера.

Точный текст новых ответов выбран здесь; это не требование пользователя о формулировках.

Для `SET-019`–`SET-022` добавить тесты в `internal/config/config_test.go`,
`internal/features/chatsettings/provider_test.go` и проверку отображения в тестах команды:
отсутствующая env-переменная даёт `1`; явно заданные `0` и дробное значение сохраняются;
отсутствующее и частичное переопределение чата берут глобальное значение; сохранённые `0`
и `0.75` побеждают дефолт; после сброса возвращается действующее глобальное значение.
Для показа `/settings` проверить строку `photo_chance: 1.00 (по умолчанию: 1.00)`.
В тесте отсутствующей переменной действительно удалить её из окружения с восстановлением
после теста: пустая строка для envconfig не равнозначна отсутствию.

### Покрытие до и после архивации

`specs/chat-settings/capability.yaml` внутри change содержит целевые статусы покрытия дельты,
а не утверждение о наличии тестов сейчас. Living specs на этапе планирования не меняются.

Существующий `specctl verify` читает сценарии только из `openspec/specs`, поэтому якорь на новый
ID из активной дельты до archive считается ссылкой в пустоту. Тесты новых сценариев написать
до ревью, соответствие указать в этом change. Якоря для существующих `SET-005`–`SET-010` добавить
при реализации, одновременно переведя эти записи living `capability.yaml` в `covered`.
Якоря `SET-013`–`SET-022` и их записи в living `capability.yaml` добавить в одном шаге с archive
после ревью. Затем повторить полный гейт. Инструментарий ради этой доработки не расширяется.

## Risks / Trade-offs

- Бот без административных прав может не получить роль пользователя → перед выкладкой
  проверить его роль в целевых чатах. Telegram гарантирует `getChatMember` для других
  пользователей только боту-администратору:
  [документация](https://core.telegram.org/bots/api#getchatmember). При ошибке доступ закрыт.
- Команда обычного пользователя зависит от доступности Telegram и добавляет один запрос →
  короткий ответ при ошибке; кеш допуска не вводится.
- Права могут измениться между проверкой и действием → использовать результат свежего запроса
  для одного вызова; Telegram не предоставляет транзакцию проверки роли и изменения настроек.
- Старое наблюдение «прав доступа команда не проверяет» станет неверным → убрать его из
  living spec при archive; `AGENTS.md` обновить при реализации, не перезаписывая `CLAUDE.md`.
- В окружении может быть явно задано прежнее значение вероятности → новый встроенный дефолт
  не заменяет его; при проверке нового поведения использовать окружение без такого значения.

## Migration Plan

Миграции БД и новые переменные окружения не нужны. После автотестов проверить в тестовой группе
обычного участника, администратора, владельца и анонимного администратора; снять права
с пользователя и повторить команду. Отдельно проверить отказ при недоступной проверке роли.
Без env-переопределения проверить `photo_chance = 1` в `/settings`, сохранность явно заданного
значения и возврат к `1` после сброса. Обновить в `AGENTS.md` обе таблицы вероятности по умолчанию.
Развернуть обычным релизом после ревью, archive и успешного CI. Откат предыдущей версии
вернёт прежнюю доступность `/settings` всем участникам и встроенный дефолт фото `0.75`;
сохранённые настройки останутся совместимы.
