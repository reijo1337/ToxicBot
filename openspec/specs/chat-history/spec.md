# chat-history

## Purpose

Что бот помнит из чата: кольцевой буфер последних сообщений, из которого собирается контекст для
LLM, и его переживание перезапусков через SQLite.

## Requirements

### Requirement: Буфер помнит последние сообщения чата
Буфер SHALL хранить ограниченное число последних записей на чат и вытеснять самые старые при
переполнении.

#### Scenario: [HIST-001] запись сохраняется целиком
- GIVEN пустой буфер
- WHEN в чат добавлена запись
- THEN она возвращается со всеми полями: автор, текст, время, идентификатор

#### Scenario: [HIST-002] история нового чата пуста
- GIVEN чат, в который ещё ничего не добавляли
- WHEN запрашивается история
- THEN возвращается пустой список, а не ошибка

#### Scenario: [HIST-003] чаты не видят друг друга
- GIVEN записи добавлены в два разных чата
- WHEN запрашивается история одного из них
- THEN возвращаются только его записи

#### Scenario: [HIST-004] переполнение вытесняет старое
- GIVEN буфер заполнен до предела
- WHEN добавляется новая запись
- THEN самая старая запись выпадает, число записей не превышает предел

#### Scenario: [HIST-005] пачка записей добавляется целиком
- GIVEN буфер чата
- WHEN добавляется несколько записей одним вызовом
- THEN они попадают в историю в том же порядке, а пустая пачка ничего не меняет

#### Scenario: [HIST-006] одновременный доступ безопасен
- GIVEN несколько горутин пишут и читают один буфер
- WHEN операции идут параллельно
- THEN данные не повреждаются и гонок нет

#### Scenario: [HIST-007] неположительный размер буфера недопустим
- GIVEN размер буфера нулевой или отрицательный
- WHEN буфер создаётся
- THEN создание падает немедленно, а не при первом использовании

### Requirement: История переживает перезапуск бота
При наличии хранилища буфер SHALL подгружать историю чата и сохранять изменения, оставаясь
работоспособным при отказах хранилища.

#### Scenario: [HIST-008] история подгружается при первом обращении к чату
- GIVEN в хранилище есть история чата, а бот только запустился
- WHEN к этому чату обращаются впервые
- THEN история читается из хранилища один раз и дальше берётся из памяти

#### Scenario: [HIST-009] изменения сохраняются
- GIVEN буфер с хранилищем
- WHEN добавляется запись или пачка записей
- THEN состояние чата сохраняется, для пачки — одним сохранением на вызов

#### Scenario: [HIST-010] в хранилище уходит обрезанная история
- GIVEN буфер переполнен
- WHEN состояние сохраняется
- THEN в хранилище уходит уже обрезанный набор записей, а не весь поток

#### Scenario: [HIST-011] отказ чтения не роняет бота
- GIVEN хранилище отвечает ошибкой на чтение
- WHEN бот обращается к истории чата
- THEN ошибка попадает в лог, буфер остаётся пустым, попытка повторяется при следующем обращении

#### Scenario: [HIST-012] хранилище починилось — история возвращается
- GIVEN чтение раньше падало, а теперь хранилище отвечает
- WHEN бот снова обращается к чату
- THEN сохранённая история подхватывается, накопленное в памяти не теряется

#### Scenario: [HIST-013] отказ записи не теряет память
- GIVEN хранилище отвечает ошибкой на запись
- WHEN бот добавляет запись
- THEN запись остаётся в памяти и продолжает участвовать в контексте

#### Scenario: [HIST-014] бот работает без хранилища
- GIVEN буфер создан без хранилища
- WHEN бот добавляет и читает записи
- THEN всё работает как раньше, только без переживания перезапуска

### Requirement: Хранилище истории изолирует чаты
Таблица истории SHALL хранить состояние каждого чата отдельно и заменять его целиком при
сохранении.

#### Scenario: [HIST-015] чтение пустой истории
- GIVEN в таблице нет строк для чата
- WHEN история читается
- THEN возвращается пустой результат без ошибки

#### Scenario: [HIST-016] сохранение и чтение возвращают то же самое
- GIVEN набор записей сохранён
- WHEN история читается обратно
- THEN возвращаются те же записи

#### Scenario: [HIST-017] сохранение заменяет прошлое состояние
- GIVEN для чата уже сохранена история
- WHEN сохраняется новый набор
- THEN прошлое состояние заменяется, а не дополняется

#### Scenario: [HIST-018] хранилище изолирует чаты
- GIVEN истории двух чатов сохранены
- WHEN читается история одного
- THEN записи другого не попадают в результат

### Requirement: История сохраняет устойчивое авторство сообщений
Новые записи об участниках SHALL сохранять достоверную связь с отправителем независимо от его
имени и username. Эта связь SHALL переживать сохранение и перезапуск. Ранее сохранённая история
без таких сведений SHALL читаться без потери остальных полей, но MUST NOT получать выдуманную
связь с участником по совпадению подписи. Сообщения от имени чата или канала MUST NOT считаться
личными сообщениями произвольного пользователя.

#### Scenario: [HIST-019] авторство переживает перезапуск
- GIVEN сохранены новые сообщения двух участников с одинаковым именем
- WHEN бот перезапускается и читает историю
- THEN сообщения остаются связаны со своими отправителями и различимы друг от друга

#### Scenario: [HIST-020] прежняя история остаётся читаемой
- GIVEN история сохранена версией бота, не записывавшей устойчивую связь с отправителем
- WHEN обновлённый бот читает эту историю
- THEN автор, текст, время и связи ответов сохраняются
- AND отправитель остаётся неизвестным, даже если подпись совпала с известным участником

#### Scenario: [HIST-021] старая и новая истории сосуществуют
- GIVEN загружены прежние записи и добавлено новое сообщение с известным отправителем
- WHEN история сохраняется и читается после перезапуска
- THEN обе группы записей остаются доступны, новые сохраняют авторство, а прежним авторство не угадывается

#### Scenario: [HIST-022] отправитель от имени канала не становится участником
- GIVEN сообщение отправлено от имени чата или канала либо Telegram не сообщил личного отправителя
- WHEN сообщение записывается в историю
- THEN оно не получает подтверждённую связь с личным аккаунтом для последующего пинга

### Requirement: История сохраняет обогащение ссылок
Сведения страницы, машинное описание превью и видимая подпись скрытой ссылки SHALL сохраняться
с сообщением отдельно от исходного текста участника и оставаться доступны после перезапуска.
Чтение истории MUST NOT вызывать повторные
внешние запросы. Ранее сохранённая история без обогащения SHALL оставаться читаемой.

#### Scenario: [HIST-023] ссылки переживают перезапуск
- GIVEN сообщение сохранено с заголовком, описанием страницы и описанием превью, а у скрытой ссылки — с её видимой подписью
- WHEN бот перезапускается и читает историю
- THEN все сведения ссылки доступны у той же реплики вместе с прежним текстом и авторством
- AND чтение не вызывает загрузки страницы или описания картинки

#### Scenario: [HIST-024] история прежней версии читается
- GIVEN сохранена история без сведений о ссылках
- WHEN её читает обновлённый бот
- THEN существующие поля записей сохраняются, обогащение отсутствует
- AND URL из старых сообщений не загружаются задним числом

#### Scenario: [HIST-025] снимок истории не меняет сохранённую запись
- GIVEN вызывающий код получил историю с данными ссылки либо передал их для записи
- WHEN он изменяет сведения ссылки в своём экземпляре
- THEN содержимое сохранённой истории не меняется

### Requirement: История хранит персональные события реакций отдельно от реплик
История SHALL хранить событие реакции с автором действия, временем, целевым сообщением,
добавленными и снятыми реакциями. Событие MUST NOT считаться написанной пользователем репликой.
Оно SHALL занимать одно место в общем ограниченном окне чата наравне с другими записями.
Рабочее окно бота SHALL вмещать 100 записей.

#### Scenario: [HIST-026] событие сохраняет автора действия и цель
- GIVEN в историю добавлено изменение реакции
- WHEN читается история этого чата
- THEN доступны время, автор действия, ID целевого сообщения, добавленные и снятые реакции
- AND автор действия не превращается в отправителя собственной текстовой реплики
- AND записи другого чата в результат не попадают

#### Scenario: [HIST-027] события и сообщения делят одно окно
- GIVEN история заполнена сообщениями и событиями до общего предела
- WHEN добавляется новое событие реакции
- THEN самая старая по порядку записи запись вытесняется, а общий размер истории не превышает предел
- AND событие сохраняется, даже если исходного сообщения уже нет в окне

### Requirement: События реакций совместимы с сохранённой историей
События и их идентификаторы доставки SHALL переживать сохранение и перезапуск вместе с
остальной историей. Прежняя история без реакций SHALL оставаться читаемой. Изменение одного
переданного или возвращённого экземпляра MUST NOT менять сохранённые данные и другие снимки.

#### Scenario: [HIST-028] событие переживает перезапуск
- GIVEN история содержит обычные сообщения и событие с добавлением и снятием реакций
- WHEN история сохраняется и загружается после перезапуска
- THEN сохраняются все сообщения, авторство и поля события, включая ID апдейта
- AND чтение не вызывает запросов к Telegram за прошлыми реакциями

#### Scenario: [HIST-029] прежние записи не получают выдуманных событий
- GIVEN история сохранена версией бота без событий реакций
- WHEN новую версию запускают с этой историей
- THEN текст, авторство, время, ссылки и связи ответов остаются прежними
- AND отсутствие сведений о реакциях не считается известным пустым набором или поводом для восстановления прошлого

#### Scenario: [HIST-030] вложенные данные снимков изолированы
- GIVEN событие с добавлениями и снятиями передано для записи либо получено в снимке истории
- WHEN вызывающий код меняет поля события или элементы его коллекций
- THEN сохранённая история и другие ранее полученные снимки не изменяются
- AND одновременные чтение, запись и повторная доставка не создают гонок

### Requirement: Повторная доставка не дублирует сохранённое событие
Пока событие реакции присутствует в окне истории, повтор того же апдейта SHALL оставлять
историю неизменной. Это SHALL работать и после перезапуска. Другой апдейт с теми же действиями
MUST NOT считаться повтором только из-за совпадения содержимого.

#### Scenario: [HIST-031] повтор распознаётся по идентичности апдейта
- GIVEN событие уже есть в памяти либо было загружено после перезапуска
- WHEN тот же апдейт приходит повторно, в том числе одновременно из нескольких вызовов
- THEN остаётся одна запись, а повтор не вызывает лишнего сохранения
- AND другое изменение с другим ID апдейта принимается независимо от совпадения автора, emoji и времени

### Requirement: Ошибка первоначального чтения не заменяет сохранённую историю
При невозможности первоначально прочитать историю для записи реакции бот MUST NOT заменять её
неполным состоянием. Бот SHALL делать не более трёх попыток приёма одного события. Если
чтение не восстановилось, событие SHALL пропускаться с диагностикой ошибки и продвижением
доставки следующих апдейтов, без сохранения неполной истории.

#### Scenario: [HIST-032] временный отказ чтения не стирает прежнюю историю
- GIVEN история чата сохранена, но её первое чтение отвечает ошибкой
- WHEN бот пытается записать реакцию
- THEN запись и сохранение неполного состояния не выполняются
- AND при восстановлении чтения в пределах трёх попыток прежняя история загружается, а событие добавляется ровно один раз
- AND после трёх неудачных попыток событие пропускается с ошибкой в диагностике, последующие апдейты доставляются, а прежняя история не перезаписывается

## Наблюдения

- Размер буфера — 100 записей, задаётся при сборке зависимостей в `cmd/main.go`.
- Загрузка ленивая: пока к chatID не обратились после старта, история в памяти пуста. Это не
  потеря данных, а отложенное чтение.
- Без хранилища подставляются no-op реализации, поэтому ветка «бот без SQLite» не требует
  отдельных проверок на nil.
